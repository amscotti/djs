# v0.9.0 architecture review

## Decisions

- **OpenSSL EVP for digests/HMAC, `RAND_bytes` for randomness.** Reusing the
  system crypto library avoids carrying a hash implementation and gives
  constant-time primitives. Only `libcrypto.so.3` is linked; no provider or
  config file is loaded, so algorithm selection is fixed by name.
- **zlib streaming state in the host, not per-chunk compression.** Each
  `createGzip()` owns one `z_stream`; chunk-wise independent gzip members
  would produce a concatenation that some consumers reject and would inflate
  poorly. Both sync and stream paths share the same create/write/end native
  calls, so there is one code path to test.
- **Handles are generation-safe.** Crypto and zlib tables hand out monotonically
  increasing ids; a stale id can never address a reused slot. This mirrors the
  child-process fix and avoids the class of cross-talk bug found in v0.8.0.
- **Slots are owned by a runtime.** `cryptoCloseAll`/`zlibCloseAll` only free
  slots whose `Runtime*` matches, so embedding two runtimes does not let one
  teardown free the other's live hash.

## Findings and dispositions

1. **Unbounded decompression (zip bomb).** `inflateSync` and the gunzip stream
   could allocate without limit. Fixed with a 256 MiB output cap
   (`zlib output limit exceeded`). Residual: the cap is per stream, so many
   concurrent streams can still exhaust memory; the 32-slot table bounds this
   at 8 GiB worst case. A global budget is future work.
2. **Transform ignored `opts.final`.** Found while wiring compression streams:
   `Transform` overwrote `_finalImpl` unconditionally, so any custom `final`
   (including `createGzip`'s trailer flush) never ran and the gzip stream was
   truncated. Fixed in the prelude and covered by the streaming round-trip
   test. This was a latent bug for every Transform user, not only zlib.
3. **`toStringView` coerces any value to a string.** Both crypto and zlib
   originally used it as a bytes accessor, so a Buffer was hashed/compressed
   as its string representation. Fixed by gating on `jsIsString` before
   coercing; the binary hash and all-256-bytes zlib tests are the regression
   guards. Other call sites in `child.d`/`process.d` still use `toStringView`
   for values that are documented strings; no byte paths remain.
4. **OpenSSL `HMAC_*` is deprecated in 3.0.** Kept for a small ABI surface;
   an EVP_MAC migration is an ADR candidate, not a correctness issue.
5. **`libcrypto.so.3` by soname is Linux-specific.** Recorded in PINS and the
   v1.0 portability finding; packaging must declare the runtime dependency.
6. **zlib `Z_BUF_ERROR` handling.** A truncated stream must raise rather than
   return partial data; the `end` path checks `ended` explicitly and the
   `write` loop treats no-progress `Z_BUF_ERROR` as end-of-input.

## Residual risks

- A digest/HMAC handle that is never digested is only released at runtime
  teardown; the 64-slot table makes exhaustion a clean error, not a leak.
- Compression output is limited but input is not; callers can still feed
  terabytes through a stream over time.
- `EVP_DigestFinal_ex` writes at most 64 bytes; adding an algorithm with a
  larger digest would need a size check (currently impossible with the fixed
  algorithm list).
