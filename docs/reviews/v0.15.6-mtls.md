# v0.15.6 — mutual TLS server verification

## Implemented

- `tls.createServer({caFile, requestCert})` verifies client certificates:
  - `caFile` loads the trust bundle and enables `SSL_VERIFY_PEER`
  - `requestCert: true` adds `SSL_VERIFY_FAIL_IF_NO_PEER_CERT`
- `tls.peerAuthorized(id)` reports whether the peer presented a chain that
  verifies; `secureConnection` sockets now carry `authorized`.
- Client `certFile`/`keyFile` from v0.15.5 are exercised end-to-end.

## Application review

| # | Severity | Finding | Verification |
|---|---|---|---|
| 1 | high | server accepted any client with no certificate | `requestCert` + CA; mutual TLS succeeds only with the client cert |
| 2 | high | `socket.authorized` was always false on server sockets | `peerAuthorized` reads verify result + peer cert; prints true |
| 3 | medium | client certificate options were untested | mTLS golden uses client.pem/client.key |
| 4 | medium | missing-certificate rejection was not observable in a bounded test | documented as residual; server closes but the client error path is slow |

## Verification

`tests/js/tls_mtls.js` golden:
`server-authorized true`, `client-secure true`, `body mtls-ok`. Full gate 14/14.

## Residual

- A client that omits the certificate does not receive a prompt `error`/`close`
  in the current test window; the server rejects, but the client-side failure
  propagation needs work.
- No ALPN **selection** on the server, so HTTP/2 over TLS is still unavailable.
- PEM strings are still treated as file paths.
- No certificate chain inspection (`getPeerCertificate`) or CRL/OCSP.
