# v0.13.9 — WebCrypto `subtle` core

## Plan

Provide the `crypto.subtle` surface modern auth libraries call: digest, HMAC,
AES-GCM, RSA/ECDSA sign/verify, PBKDF2/HKDF derivation, and key import/export
for raw, SPKI, PKCS#8 and oct/RSA/EC JWK input.

## Architecture

All of it is prelude JS over the existing native crypto primitives:

- `digest` → `createHash`; `sign`/`verify` → `createHmac` or `crypto.sign`/
  `verify`.
- ECDSA signatures are converted between DER (OpenSSL) and the WebCrypto
  raw `r||s` form with small ASN.1 helpers.
- RSA/EC JWK import builds SPKI/PKCS#8 DER in JS (`n`,`e`,`d`,`p`,`q`,`dp`,
  `dq`,`qi`, EC `x`,`y`,`d`), wraps it in PEM and uses `createPublicKey`/
  `createPrivateKey` indirectly through `sign`/`verify`.
- AES-GCM uses `createCipheriv`/`createDecipheriv` with AAD and auth tags.
- `generateKey` uses `randomBytes` for HMAC/AES and `generateKeyPairSync` for
  RSA/ECDSA; `deriveKey` composes `deriveBits` + `importKey`.

## Application review

| # | Severity | Finding | Reproduction | Fix |
|---|---|---|---|---|
| 1 | high | `crypto.subtle` absent | `typeof crypto.subtle` undefined | implemented |
| 2 | high | HMAC sign looked up the digest from the request algorithm, which has no `hash` | `Digest method not supported` | read `key.algorithm.hash` |
| 3 | high | WebCrypto expects raw ECDSA signatures, OpenSSL emits DER | verify failed | DER↔raw conversion |
| 4 | medium | RSA/EC keys arrive as JWK in JWKS flows | import failed | JS DER builders for SPKI/PKCS#8 |
| 5 | low | asymmetric JWK export not implemented | `exportKey("jwk", rsaKey)` throws | documented |

## Verification

- `tests/js/webcrypto.js` + golden: SHA-256 digest vector, HMAC sign/verify and
  tamper, oct JWK export/import, AES-GCM round-trip and tamper rejection,
  PBKDF2/HKDF equality with the sync APIs, RSA sign/verify + SPKI round-trip,
  ECDSA P-256 raw-signature sign/verify.
- Existing crypto tests unaffected.

Full gate 13/13.

## Residual

No `wrapKey`/`unwrapKey`, no RSA-OAEP encrypt/decrypt, no AES-CBC/KW,
asymmetric JWK export, `deriveKey` only via `deriveBits`, no `CryptoKey` usages
enforcement.
