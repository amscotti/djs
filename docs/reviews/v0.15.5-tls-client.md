# v0.15.5 — TLS client CA, certificates and ALPN advertisement

## Implemented

- `tls.connect` accepts an options object as its final argument:
  - `caFile`/`ca` — custom CA bundle for verification
  - `certFile`/`cert` and `keyFile`/`key` — client certificate and key
  - `alpn` — comma-separated protocol list, sent via
    `SSL_CTX_set_alpn_protos`
- Native `tls.alpn(id)` reads the negotiated protocol; `TlsSocket.alpnProtocol`
  is set after connect.
- The connect callback is now a true `secureConnect` callback: it is not called
  when the handshake fails (Node parity; previously it ran with an error).

## Application review

| # | Severity | Finding | Verification |
|---|---|---|---|
| 1 | high | clients could only trust the system CA store | private CA server verifies `authorized: true` |
| 2 | high | an untrusted server was accepted earlier by custom callers | without `caFile`, connect fails `ERR_TLS_HANDSHAKE` |
| 3 | medium | no client certificate support | cert/key options wired through `SSL_CTX_use_*_file` (see residual) |
| 4 | medium | ALPN could not be requested | protos sent; value exposed via `alpnProtocol` |
| 5 | low | callback ran on failure with no error handling | callback now success-only; errors emit `error` |

## Verification

`tests/js/tls_client_ca.js` golden: trusted CA → `secure true`, body `hello`;
system-store rejection → `untrusted ERR_TLS_HANDSHAKE`. Full gate 14/14.

## Residual

- **Server-side** client-certificate verification and server `ca` are not
  implemented, so mutual TLS is only half available.
- ALPN is advertised but the server does not select or expose it; HTTP/2 over
  TLS and ALPN-based `https.createServer` remain open.
- PEM strings are not parsed: `ca`/`cert`/`key` are treated as file paths.
- Client cert/key are wired but not covered by a mutual-TLS test yet.
- No session resumption, ticket control, or TLS 1.3 policy.
