# v0.15.7 — server ALPN selection and HTTP/2 over TLS

## Implemented

- TLS server ALPN selection (`SSL_CTX_set_alpn_select_cb`), server-preference
  order; negotiated value exposed as `socket.alpnProtocol`.
- `http2.createSecureServer({cert, key, alpn})` wraps the TLS server and hands
  only `h2`-negotiated sockets to `H2Session`.
- `http2.connect("https://…", {caFile, certFile, keyFile})` performs TLS with
  ALPN `h2` before the HTTP/2 preface.
- Client and server mTLS/CA options flow into the secure HTTP/2 path.

## Application review

| # | Severity | Finding | Verification |
|---|---|---|---|
| 1 | high | ALPN was advertised but never selected | client offers `http/1.1,h2`, server prefers `h2`, both see `h2` |
| 2 | high | HTTP/2 was h2c-only | secure server + TLS client exchange a request/response (`secure-h2`) |
| 3 | high | non-h2 clients could reach the HTTP/2 state machine | secure server destroys sockets whose ALPN is not `h2` |
| 4 | medium | custom CA could not be used for h2 | `http2.connect` passes `caFile`/client certs to `tls.connect` |
| 5 | low | ALPN preference was per-context | preference is set immediately before the synchronous `SSL_accept` and cleared after |

## Verification

- `tests/js/tls_alpn.js`: `server-alpn h2`, `client-alpn h2`, `alpn-ok`
- `tests/js/http2_tls.js`: `server-stream GET /tls`, `client-body secure-h2`
- full gate 14/14

## Residual

- HTTP/2 trailers/flow-control remain the pre-existing subset; this release
  only adds the TLS transport.
- ALPN preference is a fixed static window, not a per-context configuration;
  synchronous accepts make that safe, but concurrent native handshakes would
  need ex-data.
- No `https.createServer` ALPN routing yet (choose HTTP/1.1 vs h2 on the same
  port); the secure h2 server is a separate constructor.
