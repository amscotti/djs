# v0.9.0 application review

Review of the crypto/zlib change set against the runtime, not just the new
code. Every finding below was reproduced before the fix.

| # | Severity | Finding | Reproduction | Impact | Disposition |
|---|---|---|---|---|---|
| 1 | critical | Byte APIs used `toStringView`, which coerces any value with `JS_ToCString`. A Buffer passed to `hash.update` or `zlib.*` was hashed/compressed as its **string representation**. | `crypto.createHash("sha256").update(Buffer.from([0,255])).digest("hex")` differed from Node; `inflateSync(deflateSync("hello"))` failed with `incorrect header check`. | Wrong digests for binary input (silent auth/token bug) and decompression of every Buffer failed. | Gate on `jsIsString` before coercion; binary-vector and all-256-byte tests added; Node diff now covers binary HMAC/hash. |
| 2 | high | `Transform` overwrote `_finalImpl`, so `opts.final` was never called. | `new Transform({final(cb){...}})` never logged; `createGzip` produced 10 bytes (header only) and lost the trailer. | Silent truncation of every stream that relies on `final`; compressed streams were unusable. | `Transform` only installs the default `final` when the caller did not supply one. gzip stream round-trip test covers the path. |
| 3 | high | Unbounded decompression output. | A small `gunzipSync` input expanding past RAM was buffered fully (`realloc` doubling) until OOM. | Local denial of service from any compressed input. | 256 MiB per-stream cap with `zlib output limit exceeded`; documented residual (32 streams × 256 MiB). |
| 4 | medium | Crypto/zlib slots were global and teardown freed every slot, not just the runtime's. | Embedding two runtimes and tearing one down would free the other's live `EVP_MD_CTX`/`z_stream`. | Use-after-free in an embedding scenario; not reachable from the CLI. | Slots record `Runtime*`; teardown filters by it. |
| 5 | low | `randomBytes(1.5)` silently truncated via `|0`. | `crypto.randomBytes(1.5).length === 1`. | Surprising API, diverges from Node's range error. | `Number.isInteger` check, TypeError. |
| 6 | low | A hash/zlib handle that is abandoned is only freed at teardown. | Create 64 hashes without digesting → `crypto table exhausted` until exit. | Bounded (64) and reports a clean error, but a long-lived process leaks memory. | Documented; a finalizer-based release is not worth the complexity pre-1.0. |

## Test coverage added

- Known-answer vectors: SHA-256/SHA-1/MD5 of `abc`, SHA-512 length, RFC-style
  HMAC, base64 digest, chunked update.
- Binary safety: hash and HMAC over `[0, 255, 1, 128]`, zlib round-trip of all
  256 byte values — these fail if the string-coercion bug returns.
- Lifecycle errors: unknown algorithm, double `digest`, unequal
  `timingSafeEqual` lengths.
- zlib: gzip magic, gzip/deflate/raw round-trips, empty input, truncated input
  (`Z_BUF_ERROR`), 600 KB streaming gzip→gunzip through the Transform.
- Node differential (`tests/diff/crypto.js`) compares every digest, HMAC
  (including binary key/data), `timingSafeEqual` and the zlib round-trips.

## Verification

`scripts/gate.sh` 10/10 (abi, no-phase-refs, build, unittest, permissions,
integration 90, sanitize 54 cases, net, diff 11 cases, soak). ASan/LSan clean
on `crypto` and `zlib`.

## Residual gaps

- No cipher/AES, KDF, certificate, `sign`/`verify`, WebCrypto or `crc32`.
- `digest("base64url")` is untested; the Buffer decoder may not implement it.
- Compression level is passed through but only `-1..9` is exercised; strategy
  and flush modes are not exposed.
- No concurrency test for many simultaneous compression streams (table is 32).
