# v0.13.4 — incremental HTTP responses

## Plan

Remove the last honesty caveat from v0.13.3: the HTTP client buffered the whole
response before parsing, so `response.body` yielded one chunk. Streaming AI
clients need headers first and body chunks as they arrive.

## Architecture

The client no longer waits for `end`. `ClientRequest.end` now runs a small
incremental parser over socket data:

- accumulate only until `\r\n\r\n`, cap headers at 16 KiB, emit `response`
  immediately with an `IncomingMessage`;
- choose a body mode from the headers: `content-length`, `chunked`,
  `close`-delimited, or none for `HEAD`/204/304;
- feed each decoded piece into `message.push()` as it arrives, enforce the
  64 MiB cap on the running total, and `push(null)` on completion;
- chunked decoding keeps its own buffer and a two-phase (`size` → `data`) state
  machine, so a chunk split across packets is fine.

`fetch` already built a `ReadableStream` around `res.on("data")`; that stream
now receives real chunks instead of one terminal buffer.

## Application review

| # | Severity | Finding | Reproduction | Fix |
|---|---|---|---|---|
| 1 | high | responses were parsed only in the socket `end` handler, discarding arrival boundaries | `fetch_stream` showed `chunks 1`, first token = total latency | incremental parser, emit on headers |
| 2 | medium | `Buffer#indexOf(string)` is unreliable in this runtime (seen earlier in WebSocket work) | header terminator search failed | byte-sequence `findBytes` helper |
| 3 | medium | no body-mode handling meant `content-length`/chunked/HEAD were all "read to close" | HEAD and 204 would hang or over-read | explicit mode selection |
| 4 | low | the refactor dropped the socket creation block; test caught `socket is not defined` immediately | `fetch_stream` | restored |
| 5 | low | chunk buffer concatenation is O(n²) for pathological chunk counts | large chunked bodies | acceptable at current caps; noted |

## Residual

Request bodies are still buffered before send; no keep-alive on the client;
`content-encoding` is not decoded automatically; 1xx interim responses are not
surfaced. `worker_threads` is v0.13.5.
