# v0.15.9 — worker_threads API (child-process backed)

## Implemented

- `worker_threads` no longer throws `ERR_WORKER_THREADS_UNSUPPORTED`.
- `Worker(filename, {workerData, env, eval})` starts a child djs runtime over
  fork IPC; `postMessage`/`message`, `error`, `exit`, `terminate()` (Promise),
  `ref`/`unref`.
- `isMainThread`, `threadId`, `workerData`, `parentPort` with `postMessage` and
  `message` events.
- `eval: true` writes the code to a temporary entry file and removes it on
  worker exit.
- `MessagePort`/`MessageChannel` exist for same-process coordination.

## Application review

| # | Severity | Finding | Verification |
|---|---|---|---|
| 1 | high | `worker_threads` was a hard throwing stub | file worker returns `21`; eval worker returns `5` |
| 2 | high | no worker data channel | `workerData.n * 7` round-trip |
| 3 | high | no lifecycle | `terminate()` resolves after `exit`; both workers terminate cleanly |
| 4 | medium | eval workers would need a real file | temp entry written and unlinked on exit |
| 5 | medium | package/API could be mistaken for real threads | documented below as a process-backed shim |

## Verification

`tests/js/worker_threads.js`: `worker-message 21`, `terminated`,
`eval-message 5`, `eval-terminated`. Full gate 14/14.

## Residual

- **Not real threads.** Each worker is a child process with its own runtime;
  there is no shared memory, `SharedArrayBuffer`/`Atomics`, or transferable
  objects. `transferList` is ignored.
- `MessagePort` only links ports in the same process; cross-worker channels are
  not implemented.
- No `resourceLimits`, `stdin`, `worker.performance`, or debugger/inspector
  integration.
- Worker stdout/stderr are piped but not wired into the parent by default.
- This is the compatibility-focused shim; a native isolated-runtime-per-thread
  design remains future work.
